# 项目架构落地说明

## 分层

```text
入口
  ↓
场景层 scenes
  ↓
世界层 gameplay/world
  ↓
实体、系统、战斗与机关
  ↓
状态、事件、配置仓库、存档与输入服务
```

场景层只负责启动、暂停、结算和场景切换。游戏规则放在玩法模块中，UI 不直接修改玩家实体。

## 数据驱动

- schema、字段版本、迁移和跨项目校验由 `platform_contract` 统一定义。
- `data/configs/actors.json`：玩家、敌人和 NPC 的基础属性与外观。
- `data/configs/skills.json`：近战技能范围、前摇、冷却和伤害倍率。
- `data/configs/items.json`：道具定义。
- `data/levels/*.json`：地形、出生点、道具、敌人、机关、闸门和出口。

新增敌人时，应先增加技能和角色配置，再在关卡对象层放置实例。只有出现全新的行为时，才需要新增系统代码。

## 存档边界

存档保存的是普通 JavaScript 数据：

- 玩家位置、生命与基础属性
- 背包物品
- 剧情章节与标记
- 任务状态与进度对象
- 机关状态
- 已击败敌人和已拾取物品的稳定 ID

不会保存 Sprite、物理刚体、攻击特效或投射物。活着的敌人读档后回到出生点，保证读档结果稳定。

## 输入可移植性

`InputService` 将键盘和鼠标转换为逻辑动作。以后增加手机触屏时，应实现相同动作接口，而不是在 `Player` 中直接判断触摸坐标。

## 地图编辑器接入点

地图编辑器只需要输出 `data/levels` 中的同结构 JSON。游戏不依赖地图的生成方式，也不会根据某个关卡名字写特殊分支。

## 玩法系统注册

运行时系统通过 `GameplaySystemRegistry` 安装和更新。新增玩法模块时应注册自己的创建、安装与逐帧更新入口，不向 `GameWorld.update()` 直接追加玩法条件分支。
